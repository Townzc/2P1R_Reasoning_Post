## 1. 为什么做这个实验

P008 加上 10 月 14 日的三个探索性实验，结论是：在 GSM8K + Qwen2.5-1.5B LoRA 学生 + 同源 1.5B 数学教师这个设定下，

1. 学生大约 100 个教师答案后就进入平台；
2. 用错误终答训练只低 2–3 pp（934 对 969）；
3. 第 3 次以后的重试大多花在难题或标签有问题的题上。

所以预算怎么分配，对学生准确率没有可重复的影响。分配策略要有作用，前提是学生在“更多不同的教师数据”上还能继续提升。本实验只回答一个问题：

> **H1：存在一个（任务, 学生）组合，在固定训练计算量（fixed training compute）下，学生准确率仍随不同教师答案的数量明显上升。**

这是一个门控实验（gate）。只有它找到这样的设定，后续的分配实验和正确/错误配对实验才值得做。

## 2. 沿用 P008 的固定部分

| 项目 | 取值 |
|---|---|
| 教师 | Qwen2.5-Math-1.5B-Instruct，采样参数与 P008 教师池完全相同 |
| 微调方式 | LoRA r16，其余 LoRA 配置与 P008 相同 |
| 学习率 | 形状与 P008 相同：线性 warmup 占总步数 6.25%，升到 1e-4，再 cosine 降到 1e-5；按总步数等比缩放 |
| 训练量（**有改动**） | **1,024 次更新 / 2,097,148 个监督 token**，即 P008 T1 的 4 倍（理由见 §5.2）。所有 n 用同一训练量 |
| 种子 | 主序列 seed 17；重复序列 seed 29。种子同时决定题目抽样和训练随机性 |
| 模型选择 | 不做 checkpoint 选择，只评测最后一步 |
| 评测 | 贪心解码（greedy）。GSM8K：max_new_tokens 512，上下文 2048。MATH：max_new_tokens 1024，上下文 2048。截断（length cap）一律算错 |
| 评测引擎（**有改动**） | vLLM，见 §6。本实验所有臂（arm）都用同一个引擎 |

## 3. 候选设定（每个只改一个轴）

| 代号 | 任务 / 训练池 / 测试集 | 学生 | 教师数据 | 作用 |
|---|---|---|---|---|
| **NC** | GSM8K / P008 训练池 / GSM8K test 1,319 | Qwen2.5-1.5B base | 复用 P008 D1 池，不调用新模型 | **负对照**（negative control）：预期是平的 |
| **S1** | MATH / MATH train 7,500 / MATH-500 | Qwen2.5-1.5B base | 新生成（§4） | 换任务 |
| **S2** | GSM8K / P008 训练池 / GSM8K test 1,319 | 非 Qwen、约 1B 的 base 模型，候选：Llama-3.2-1B、OLMo-2-0425-1B | 复用 P008 D1 池 | 换学生 |

几点说明：

- **S2 的分词器不同**：教师文本需要用学生的分词器重新编码，并在末尾加上学生自己的 EOS。采购成本仍按教师 token 计；监督 token 数按学生 token 计。
- **S2 的候选选择**：Llama-3.2-1B 是 gated 模型，需要负责人在 Hugging Face 接受许可。拿不到时只评估 OLMo。OLMo-2 的中期训练（mid-training）包含数学数据，可能像 Qwen 一样已有潜在能力，这正是 Stage 0 要测的。
- **MATH-500 与 MATH 训练集互不重叠**。教师可能在后训练中见过 MATH 训练题，这一点记录在案，不影响学生端的比较。

## 4. Stage 0：基线与教师池（不训练学生）

**P0 一致性检查（parity check）。** 用 vLLM 重新评测两个已有模型，并与 P008 的 HF 逐题结果比较：P008 的 969 学生（d1_b1_p0_breadth_t1）和 base 0-shot（638）。判定见 §6。

**P1 MATH 评分器冻结（grader freeze）。**
- 答案提取：取最后一个 `\boxed{}`。
- 等价判断：用固定版本的 `math-verify`，失败时回退到规范化字符串比较。
- 先在教师输出上运行。“字符串比较”和 `math-verify` 结论不一致的样本中，抽 50 条逐条核对（AI 判断，负责人抽查）。
- 核对后记录评分器的 sha 并冻结，之后不得再改。

**P2 MATH 教师池。**
- MATH train 全部 7,500 题，每题采样 1 次。
- 另随机抽 500 题，每题多采 3 次（共 4 次），用于估计各次尝试的成功率。
- 每题的“正确答案”定义为：第一次被冻结评分器判为正确、以 EOS 正常结束、没有截断的输出。

**P3 基线评测。** 对每个候选学生测 0-shot 和 4-shot（示例取自 dev，与测试集不重叠），同时测教师在同一测试集上的 0-shot 准确率。

**G0 门槛（进入 Stage 1 的条件），按设定分别判定：**
- 教师准确率 − 学生 0-shot 准确率 ≥ 20 pp；
- 技术有效：截断比例 ≤ 15%，技术性未知（technical unknowns）= 0；
- S2 若两个候选都通过，选“教师 − 学生 4-shot”差距更大的那个。

以下两项**只报告，不作门槛**：

| 指标 | 不作门槛的原因 |
|---|---|
| 4-shot 补回的差距比例 | 核对后发现，Qwen/GSM8K 按“< 50%”这条也会通过（按教师报告值约 85% 估算，补回约 40%），而我们已知它会饱和，所以这条没有区分力 |
| 教师首次尝试成功率 | 它只决定“重试”这个杠杆有没有意义；对 breadth/depth 的差别和数据量曲线不是必要条件 |

## 5. Stage 1：固定计算量下的学习曲线

### 5.1 臂

- 对通过 G0 的每个设定，取 n ∈ {100, 400, 1,600, 3,200} 条正确的教师答案，每题 1 条。
- 题目来自 seed 17 的一个固定随机排列，取前 n 个，形成嵌套子集：100 ⊂ 400 ⊂ 1,600 ⊂ 3,200。
- 重复序列：seed 29，换一个新的排列，只做 n = 400 和 n = 3,200。
- 负对照 NC：只做 seed 17 的 n = 400 和 n = 3,200。

| | 每个设定的运行数 |
|---|---:|
| S1 / S2 | 4 + 2 = 6 |
| NC | 2 |
| **最多合计** | **14**（两个设定都通过时） |

### 5.2 为什么是 1,024 次更新 / 2,097,148 个 token

- 要保证最大的 n = 3,200 至少完整训练一遍。GSM8K 答案平均约 350 token（3,200 条约 1.1M），MATH 约 500 token（约 1.6M），都需要比 P008 T1 的 524k 更多的训练量。
- 所有 n 用同一个训练量，曲线才只反映“不同答案的条数”，避开 P008 里预算和训练量一起放大的混淆。
- 代价是小 n 会被重复很多遍（n = 100 时约 40–60 遍），可能过拟合，把小 n 的准确率压低，造成斜率虚高。所以**门控只比较 n = 400 和 n = 3,200**。n = 400 的重复次数（GSM8K 约 15 遍）和 P008 的 100 条 T1 学生相当，后者没有表现出明显过拟合。n = 100 和 n = 1,600 只用来描述曲线形状。

### 5.3 G1 判定规则（预注册）

一个设定判为“仍在学习”，需要同时满足：

1. seed 17 序列中，acc(n = 3,200) − acc(n = 400) ≥ **5.0 pp**；
2. 在题目层面做配对 bootstrap（10,000 次重采样），这个差值 95% 置信区间的下界 > 0；
3. seed 29 序列中，同一差值 ≥ **2.5 pp**，且方向相同。

根据结果的处理：

- **负对照 NC 的差值 ≥ 5.0 pp**：说明新的训练量设计本身制造了斜率。停止，报告，不认定任何设定通过。
- **两个设定都通过**：选 seed 17 差值更大的。两者相差不到 1 pp 时选 S1，因为在 MATH 上重试更有意义。
- **都不通过**：停止。结论是“分配不敏感”在换学生和换任务后依然成立，与负责人讨论转向。不再追加花费。

### 5.4 运行顺序与提前止损（futility）

1. 先跑 seed 17 的 n = 400 和 n = 3,200：NC 先跑，然后是各个通过 G0 的设定。
2. **科学信号检查（A4）**：这几对跑完后立刻向负责人汇报。如果每个候选设定的差值都 < 2.0 pp，剩下的运行全部取消，直接报告。
3. 否则再跑 n = 100、n = 1,600 和 seed 29 的重复序列。

## 6. 评测引擎：vLLM 与一致性检查

两种引擎的区别：
- **HF `generate`** 是静态批处理：一批 16 条一起解码，要等最长的那条结束，没有分页 KV cache，所以很慢。探索性实验里，1,239 道题花了 2,389 秒，约 $2.92。
- **vLLM** 是推理引擎，用 PagedAttention 和连续批处理（continuous batching），吞吐量通常高一个数量级以上。
- 贪心解码理论上两者结果相同。但计算核（kernel）和批次组成不同，bf16 的累加误差也不同，会让少量题目的输出在某个 token 处分叉，最终答案翻转。这是数值差异，不是 bug。

实现要求：
- 固定 vLLM 版本，用 bf16；
- 直接传入 prompt 的 token ID，不让引擎重新分词；
- temperature 0；只在 EOS 处停止；max_tokens 按 §2；
- LoRA 先合并（merge）进权重，再评测；
- 保存原始 token ID，评分在 CPU 上离线进行，沿用 P008 冻结的 `first_stop` / `completion_score`，生成和评分分开。

P0 判定（969 学生和 base 0-shot 两个模型分别判定）：

| 准确率差 | 处理 |
|---|---|
| ≤ 1.0 pp，且逐题不一致率 ≤ 4% | 通过；新结果可以和 P008 的数字并列展示 |
| 1.0–3.0 pp | 继续；本实验内部的比较不受影响，但不和 P008 的数字混用 |
| > 3.0 pp | 视为实现错误（prompt、模板或 EOS 处理），停止排查，不进入 Stage 0 的其他步骤 |

- **超时上限**：每个 worker 有 max_seconds 上限，超时即停。
- **延迟计量**：账单有延迟，按已计量金额加预留额度计算，不按发票。
- **⚠ 需要负责人直接确认预算**：仓库里现有的保守核算是 $384.24 对 $450 上限（其中 $50 受保护），按这个记录**只剩约 $15.76，不够本实验使用**。你说现在约有 $300、期中后补充 $2,700。这需要你直接告诉 Codex 新的上限（例如“项目上限调整为 $X，本实验上限 $60”），我不能代为转述。
