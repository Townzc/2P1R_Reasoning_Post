# 一套可以复用的 AI 辅助科研工作流

我们采用“研究者决策、AI 分工、GitHub 保存证据”的方式。关键不是让几个模型互相聊天，而是让每一步都有可检查的产物和明确的负责人。

| 角色 | 主要职责 | 交付物 |
|---|---|---|
| 研究者 | 确定科学问题、价值判断、预算和截止时间；处理分歧 | 明确的问题与约束，最终判断和对外表达 |
| GPT Pro | 深读论文、比较已有方法、寻找竞争解释 | 论文链接和版本、具体章节、证据、与当前假设的关系 |
| Codex | 将问题变成实验；实现、测试、运行、监控、核验 | 冻结的实验设计、代码、原始结果、成本和复盘记录 |
| Claude | 针对固定版本独立审计方法和结果 | 可复现的发现、证据位置、严重程度、修正建议 |
| GitHub | 保存共同状态和版本化证据 | 当前状态入口、实验协议、日志、审计包与修订历史 |

## 一轮实验怎样推进

1. **先写一个可证伪的问题。** 明确比较对象、控制变量、结果指标，以及哪些结果会支持或反驳解释。
2. **阅读形成对照表。** 区分“别人做过什么”“论文没有回答什么”“我们准备检验什么”。模型的判断不能代替原论文证据。
3. **冻结最小实验。** 固定数据划分、模型版本、实验组、随机种子、预算、停止条件和分析方法。先做工程先导，再扩大规模。
4. **带记录执行。** 代码先提交，运行绑定提交版本；保存生成意图、原始返回、评分、检查点和费用。失败、重复及未知输出也保留。
5. **执行者先核验。** 检查文件哈希、实际训练量、评分重算、资源释放和成本。这只能叫本地核验，不能冒充独立审计。
6. **提交审计包。** 给 Claude 一个固定 commit、明确的问题、数据文件和复现命令，避免让它根据聊天摘要猜结果。
7. **处理发现，再设计下一轮。** 逐条记录接受、修正、推迟或争议；代码或证据变动后生成新版本。结果出来前定分析规则，避免追着好看的指标改实验。

简要流程：问题 → 文献证据 → 有界方案 → 工程先导 → 实验 → 本地核验 → 独立审计 → 人类判断。

## 怎样交接最省时间

每次交接只给四项：当前问题、固定 commit、证据入口、需要对方回答的问题。

论文阅读请求可以写：

> 请检查问题 X 是否已被解决。给出最接近的原始论文、版本和相关章节；区分作者实测结论、你的推断和仍未知的部分；指出实验 Y 最需要排除的竞争解释。

审计请求可以写：

> 请审计 commit <hash> 中的 <packet>。检查实验组可比性、数据泄漏、评分、实际预算、失败处理和结论边界。对每项发现给出证据路径及复现步骤；未实际检查的项目请标记未核验。

发给工程执行者可以写：

> 在已批准预算和截止时间内修复发现 F1；保留旧证据。先用保存样本验证修复，再说明是否需要新模型调用。不要重放已完成或结果不确定的工作。

## 我们目前的实践与限制

P007 的主实验与成本先导已完成本地核验，按阶段发布了审计包；同预算后续正在推进。Claude 已实际交付固定版本审计：主实验 PASS-WITH-NOTES、先导紧凑表 PASS，并指出成本比较中的高风险混杂；这些结论只覆盖报告列明的版本和范围。新数据和修改后的方案仍需要新审计。进展与分歧统一记录在 [工作总表](WORKBOARD.md)。

这套方法有额外的记录、交接和复核成本。模型之间也可能共享错误；“多个模型意见一致”不是科学证据。可靠性来自原始论文、明确的实验约束、可复现代码、独立重算和研究者的判断。

预算权限与科学评价分开：审计建议不自动授权扩组、花钱或发送消息。凭据和大文件留在私有存储，公开仓库提供安全的证据和哈希。对于课程或机构有 AI 使用限制的工作，按其规则划分允许的辅助与必须本人完成的内容。
