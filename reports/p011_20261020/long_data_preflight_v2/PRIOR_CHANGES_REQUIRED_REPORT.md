## 结论：CHANGES-REQUIRED（3 项，均小改）

代码整体质量好。以下各项都正确：
- 读入结构：OT3 是 parquet 的 `conversations` 两轮 list[dict]；AM 是 jsonl，带 `info`；
- 产出路径全部是本地 create-only，没有远端路径，也没有模型或 endpoint 循环；
- 原生 chat 模板（含默认 system）与 assistant 掩码；
- 13-gram 去污染；
- 跨来源父题合并；
- 种子定义；
- D 在过滤前先定好要用的那一行；
- 子集和的精确重构（我逐行推演过回溯逻辑，正确）；
- 失败时保留证据、不允许第二次调用。

但有两处会**直接影响科学有效性**，另有一处是**时间上不可接受**的开销。因为 `admit_code` 绑定源文件哈希，修改后需要重新提交，我会尽快复审，只看改动部分。

### R1（必改）：OT3 的剂量 B 必须取各格单遍 token 数的最大值

**现状**：`budget = once['A7']`。

**问题**：A5 (256,16) 和 A8 (1024,4) 也各有 4,096 条回答，但它们的单遍 token 总数与 A7 不同。只要其中一格比 A7 长，`whole_schedule` 就会因为 q<1 报"单遍超过 B"，这一格无法训练。计划 §1.3 的本意是"每条回答至少训练一次"，这一点优先。

**修改**：两种模式统一用 `budget = max(once.values())`，D 本来就是这样。按 FROZEN_DOSE 照常记录每格的单遍 token 数。这样 A7 不再恰好一遍，而是 q/q+1 遍，**作为计划的澄清写进披露**。

### R2（必改）：调度必须按"遍"（epoch）顺序，不能全局按长度分桶

**现状**：`whole_schedule` 把全部展示次数（stream）按 `n_processed//512` 分桶，打乱桶的顺序后**整桶连续排列**。

**后果**：
1. 同一条回答的 q 次重复全部挤在同一个桶段里，几乎是连着看到的，不是分散在多遍之中。小格（例如 A1 的 q≈16）会退化成"每条回答连续反复训练"。
2. 每条序列在余弦学习率曲线上的位置由它的长度决定。

这两点都会系统性地混淆 K 和 P 的比较，因为不同格的重复次数和长度分布不同。

**修改**：
- 第 e 遍（e=0..q−1）是全部回答的一次打乱：`random.Random(f'17:pass:{e}').shuffle(list(range(n)))`。
- 补齐用的 extras 子集单独打乱：`random.Random('17:extras')`，放在最后。
- stream 依次拼接各遍，最后接 extras。
- 去掉全局分桶。
- 切分成 U 次更新的逻辑和不变量检查保持原样。
- `length_bucket_width` 记为 null。

如果需要减少 padding，只能在**同一次更新内部**按长度排 micro-batch，这属于运行时 CR 的范围。我建议每条序列单独作为一个 micro-batch 累积梯度，按该次更新的总监督 token 数归一化，这样完全没有 padding。

**测试**：加一项测试，验证 stream 的前 q·n 个位置按遍切开后，每一遍都恰好包含每条回答一次。

### R3（必改，原因是时间）：合格性改为"按打乱顺序逐个检查，凑满即停"

**现状**：
- OT3 对全部约 5.3 万个父题、约 85 万条回答逐条做分词以检查长度；
- D 对全部共同父题（可能有数十万）各做 2 次分词。

快速分词器单线程大约每秒百万 token。OT3 的数学部分约 25GB 文本，光长度检查就要 1.5–2 小时；D 更久。在 22:00 冻结的时间线下不可接受。

**修改**（**与原规则在分布上等价**，都是从合格总体中均匀随机抽样，只是具体抽到的题不同）：

- **OT3**
  1. 候选 = 行数恰为 16 的父题，按父题键排序后用 `Random(20261020).shuffle`；
  2. 按这个顺序逐个检查完整性、去污染、长度；
  3. 合格的依次加入，**凑满 4,096 个就停**。
  - 每个检查过的父题照常写入 disposition；行数不等于 16 的父题数量仍按全池统计。
  - 剔除比例和 difficulty 直方图改为"已检查前缀"上的统计，并写明这一点。
- **D**
  1. 候选 = 共同父题，排序后用 `Random(20261021).shuffle`；
  2. 用 `choose_d_row` 选定两边各一行（规则不变），检查标记；
  3. 凑满 1,024 个就停。

我以审计方身份把这一点**记录为计划 §1.1 第 6 步和 §5 第 3 步的实现澄清**，不需要负责人另外批准，因为抽样总体和随机性质都没有改变。

## 不阻塞的注意事项

3. **A1 必须报告的内容**：AM 的 verify_score 缺失或 <0.9 的计数（计划没有要求重新过滤，所以只报告）；两份 AM 数据在共同父题上 `info.source` 是否一致。
4. **tokenizer**：1.5B 与 3B 的四个 tokenizer 文件 git blob 完全相同（含 chat template 所在的 tokenizer_config），所以共用一次编码是合理的。
5. **测试**：测试覆盖了核心边界，`exact_subset` 的穷举对照很好。R2 的新测试见上。
