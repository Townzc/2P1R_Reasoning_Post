## 3. 必须修改

### 3.1 F4 的后续要求（C6 数据构建时）

模板一致性测试用的是合成消息。主网格训练数据必须满足：

1. 训练行的 `problem` 字段写入的是**加了 OMI-2 提示词之后的完整文本**（即 `prompt_text(题目, "omi2")`），不是裸题目。否则训练时没有指令、评测时有指令。
2. 加一个端到端测试：取 3 条真实训练行，经 LLaMA-Factory 的实际预处理得到 prompt token，与评测端对同一道裸题渲染出的 token 完全相同。
3. LLaMA-Factory 超过 `cutoff_len` 会**静默截断**。C6 必须保证每条"模板 + 提示 + 解"的 token 数 ≤ 4,096，并报告最大值。R1/R2 运行前同样报告超过 8,192 的行数。

### 3.2 F5：百分号

- 实测：`18\%` 对标准答案 `18` 判错；`50\%` 对 `0.5` 判对。
- GSM8K 里有问百分比的题，标准答案是裸数字。未训练模型的 4-shot 基线容易写成 `18\%`，会被判错，使 Δ_SFT 偏大。
- **修改**：数值比较前去掉结尾的 `\%` 或 `%`；按数学值等价的路径保留。新路径单独记为 `percent_stripped`，汇总里报告各路径的条数。

### 3.3 `modal_g0.py`

1. **Llama 是 gated 模型**：`cache_model` 里 `token=False`，下载 `meta-llama/*` 会失败。改为通过 Modal Secret 读取 HF token；token 不写入任何文件或日志。
2. **评测训练出的检查点**：现在只支持 Hub 上的模型。加一条本地路径：
   - `model` 为持久卷上的检查点目录；
   - 加载前核对权重文件的 sha256 与训练时写下的 `CHECKPOINT_FILES.json` 一致；
   - manifest 记录训练的 `run_id` 和权重 sha256。
3. **完整 MATH（5,000 题）一次提交**：现在每 1,024 条一块，每块都要等最长的那条跑完。
   - 实测：Qwen-Instruct 的 MATH-500 里 21 条循环输出占了全部生成 token 的 56%，一块约 100 秒。
   - 5,000 题分 5 块约多花 400 秒（约 $0.46 / 格，40 多格就是十几美元）。
   - 主网格把 `batch_size` 设为不小于题数。

### 3.4 `modal_train.py`

1. **剂量自检**（防止跑错格）：请求里带 `cell`；校验 `dataset.rows == P × K`，并校验 `config` 与 `training_config()` 对该格生成的结果逐项相同（路径类字段除外）。
2. **主网格不存中间检查点**：
   - 现在 `save_steps=1000`，主网格 1,024 步会在第 1,000 步多存一份带优化器状态的检查点，约为模型本身的 3 倍大小，80 次训练是几百 GB，还要逐个算哈希。
   - 主网格改为只保存最终模型（`save_strategy: "no"`，或 `save_steps` 大于总步数）。
   - R1、R2 保持发布版的设置。
3. **检查点保留规则**（需负责人确认，见 §5 D5）：主网格检查点可由"数据 + 配置 + 种子"重新训练得到，不要求独立备份；评测原始输出入库并审过之后即可清理，头条对比用到的保留到 12/14。请 Codex 确认 Modal 卷是否按容量计费。
4. 说明：训练和评测是两个镜像（torch 版本不同），所以"一个容器里连训带评"做不到，接受。每次冷启动的开销请在费用探针里单独列出。

### 3.5 判分模型配置

- `li_judge.json` 的 `max_model_len` 是 32,768。按我的估算，单张 H100 放不下：
  - Qwen2.5-32B 的 fp16 权重约 61 GiB；
  - `gpu_memory_utilization=0.85` 下可用约 68 GiB；
  - 32,768 token 的 KV cache 约需 8.6 GB（每 token 约 0.26 MB）。
- vLLM 会在加载完 60 多 GB 权重之后才报错，白花几分钟 H100。
- **修改**：`max_model_len` 改为 8,192；启动前先检查最长的一条待判输入不超过它。这是估算，没有实测。

## 4. 科学信号：Li 的长链检查点本身就"停不下来"

这是 Li et al. **自己发布的** Qwen2.5-1.5B-Instruct 长链检查点，按他们自己的协议（greedy，16K 上限）评测：

- 500 题里 **245 题（49%）撞到 16,384 token 上限**。我检查了这 245 条的尾部，241 条是重复循环（比如已经得到答案后反复"再检查一遍"，或者输出一长串相同数字）。
- 这 245 题全部判错。只有 24 条里出现过 `\boxed`。
- 在正常结束的 255 题上：

| 模型 | 这 255 题上的正确率（估计口径） |
|---|---|
| 长链检查点 | 193/255 = 75.7% |
| 短链检查点 | 180/255 = 70.6% |
| 未做 SFT 的 Instruct | 162/255 = 63.5% |

- 在长链检查点撞上限的 245 题上，短链 33.1%，未做 SFT 32.2%。

**怎么理解，以及不能怎么说**

- 这与我们 P011 的现象是同一种：小数据长链 SFT 之后，小模型在 greedy 解码下大量循环。P011 不是我们独有的实现错误。
- Li 表 8 里"长链不如短链"（41.6 对 52.3），在这个检查点上主要来自不终止，而不是推理本身更差。
- **限制**：
  - 255 题是按长链模型自己能否结束选出来的，偏向它会做的题，所以 75.7 对 70.6 不是公平比较；
  - 只有一个检查点、一个基准、greedy 解码；
  - 以上都是不依赖判分模型的估计。
- 这只能作为假设，但值得在 Slack 和 OH 上向老师提出。

**附带**：短链 SFT 相对未做 SFT 的增益很小（MATH-500：52.2 对 48.2，逐题不一致 66 对 46，未达显著；GSM8K：71.95 对 68.46）。这符合预期：Instruct 学生处在"激发区"。主网格里要看 base 学生。
